## Overview

This repository is **`Mueve-TEC/soltec-localdev`** (the local-development
skeleton for the SolTec Odoo program), checked out at the path
`/home/ezeluduena/proyectos/odoo-unc/migracion/soltec-localdev-odoo19`
because the parent directory is dedicated to an Odoo **18 → 19 migration**
effort.

What it is:

- A **Docker-based localdev harness** for **Odoo 19 Community** (`FROM odoo:19.0`).
- It does **not** contain the Odoo server source itself — it rides on the
  official `odoo:19.0` Docker image and only adds **custom addons**.
- Custom addons are **vendored from several upstream repos as git submodules**
  under `submodules/`, then **flattened** into `custom-addons/` by a script
  (`copy_addons.sh`) so Odoo can consume them as a single addons path.
- It is **not** an OpenUpgrade repository. The "migration" in the path refers
  to a **source-code migration** of the Argentine localization
  (Mueve-TEC's `odoo-argentina`) from Odoo 18 to Odoo 19, performed largely
  upstream / in submodules, plus the inevitable in-place code adjustments
  (view `tree`→`list`, `attrs`→inline, `_post_init_hook(env)` signatures, etc.).

- Remote branches: `18.0`, `19.0`, `ar_fe`, `ar_fe_fiscal_ws`, `correo`,

- Branch-naming convention: **per-Odoo-version branches** (`18.0`, `19.0`)

## Environment Startup & Management

Everything runs through Docker Compose on the host (no host-level Odoo install
required). From the repo root there is a **`Makefile`** wrapping the common
flows; the raw `docker compose` equivalents are shown alongside.

| Action                                                      | Make target       | Raw command                       |
| ----------------------------------------------------------- | ----------------- | --------------------------------- |
| Build the Odoo image (first time / after Dockerfile change) | `make build`      | `docker compose build --no-cache` |
| Start all services (detached)                               | `make up`         | `docker compose up -d`            |
| Stop services                                               | `make down`       | `docker compose down`             |
| Stop + delete volumes (wipe DB/files)                       | `make down-clean` | `docker compose down -v`          |
| View Odoo logs (follow)                                     | `make logs`       | `docker compose logs -f web`      |
| Service status                                              | `make ps`         | `docker compose ps`               |
| Open a shell inside the Odoo container                      | `make shell`      | `docker compose exec web bash`    |
| Restart the web service                                     | `make restart`    | `docker compose restart web`      |

`make help` lists all targets. Variable overrides: `DB=<db>` (default `odoo`),
`MODULE=<module>` (default `base`), `TEST_TAGS=<filter>`.

Services and ports (from `docker-compose.yml`):

- **web** — Odoo 19.
  - Image: `soltec-odoo19-desarrollo:1.0` (built from `FROM odoo:19.0`).
  - Exposes host port **8069** → http://localhost:8069
  - Addons path: `/mnt/custom-addons,/usr/lib/python3/dist-packages/odoo/addons`
    (the volume `./custom-addons` is mounted at `/mnt/custom-addons`).
  - DB env: `HOST=db`, `USER=odoo`, `PASSWORD=odoo`.
- **db** — `postgres:14`.
  - User/db/password: `odoo` / `odoo` (POSTGRES_DB=postgres is the init DB only).
  - No host port exposed by default; reachable on the `odoo-network` as host `db:5432`.
  - Volume `postgres-data` persists the cluster.
- **pgadmin** — `dpage/pgadmin4`.
  - Exposes host port **5050** → http://localhost:5050
  - Login: `admin@hola.com` / `admin`
  - To connect pgadmin to the DB: host `db`, port `5432`, user `odoo`, password `odoo`.

Notes:

- There is **no `.env` file** and **no test-runner script** at
  the repo root. All config is inline in `docker-compose.yml`.
- The Odoo container's `command` only sets `--addons-path`; it does **not**
  pass `--database`, `--db-filter`, or `--test-enable`. A database must be
  created (via the Odoo web "Manage Databases" page or `createdb` style flow)
  before installing modules. Odoo 19's default behaviour will create/select a
  DB named after the master password screen on first access.
- The official `odoo:19.0` image runs Odoo 19 with Python 3 (Debian-based).
- **The `Dockerfile` is bare (`FROM odoo:19.0`) — AR Python deps are NOT
  baked in.** The migrated AR modules run on `zeep` + `pyOpenSSL` (both
  already present in the base image), so `l10n_ar_fiscal_ws*` work out of the
  box. The legacy pre-rename modules (`l10n_ar_afipws*`) and any code path
  using `pyafipws`/`pysimplesoap` need `submodules/odoo-argentina/requirements.txt`
  installed into the container; see "Python / Dependency Management" and
  Gotcha #9.

## Migration Approach

**This repo is NOT an OpenUpgrade project.** There are:

- **No** `pre-migrate.py` / `post-migrate.py` at the project level.
- **No** `openupgrade_*` scripts, `openupgrade_framework`, or `.github` OpenUpgrade workflows.
- The only `pre-migrate.py` / `post-migrate.py` files present are **per-module
  standard Odoo data migrations** under
  `custom-addons/account_payment_pro/migrations/19.0.2.11.0/` and
  `.../19.0.2.0.0/` (mirrored from `submodules/odoo-argentina/adhoc-modules/account-payment/account_payment_pro/migrations/...`).
  These are Odoo's built-in module-internal migration mechanism, invoked on
  module upgrade — nothing special.

The actual "migration" being done here is a **source-code migration of the
Argentine localization to Odoo 19**, and it is being performed **upstream in
the submodule repos**, not in `soltec-localdev-odoo19` itself. The strategy is
documented in detail in `submodules/odoo-argentina/PLAN.md`. Summary:

1. `Mueve-TEC/odoo-argentina` is the canonical AR localization repo. Its
   `19.0` branch was created from `18.0` and then **git subtree**-imported four
   ingadhoc upstream repos at their 19.0 branches under `adhoc-modules/`
   (a fifth, `account-invoicing`, was added later to provide
   `account_background_post`).
2. **Why subtree, not submodules**: Mueve sometimes edits upstream files
   in place (`[FIX-adhoc] <module>: <description>` commit prefix) but never
   pushes fixes upstream. Subtree keeps a self-contained clone and re-merges
   upstream updates via 3-way merge; submodules would require fork-backed
   reachable pins (no fork exists).
3. **Per-repo upstream tracked** (see `submodules/odoo-argentina/scripts/pull-upstream.sh`):
   - `odoo-argentina` → `https://github.com/ingadhoc/odoo-argentina.git` branch `19.0`
   - `odoo-argentina-ce` → `https://github.com/adhoc-dev/odoo-argentina-ce.git` branch `19.0-mig-MAQ` (adhoc-dev's _migration_ branch; open PR #92 to ingadhoc; this is the branch that does the actual 18→19 migration of the CE modules, including the rename `l10n_ar_afipws`→`l10n_ar_fiscal_ws`)
   - `account-payment` → `https://github.com/ingadhoc/account-payment.git` branch `19.0`
   - `account-financial-tools` → `https://github.com/ingadhoc/account-financial-tools.git` branch `19.0`
   - `account-invoicing` → `https://github.com/ingadhoc/account-invoicing.git` branch `19.0`
     (added later to provide `account_background_post`, a dependency of the
     vendored `account_ux`; all its modules are Community-edition only)
4. To pull upstream updates **inside `submodules/odoo-argentina/`** (a
   separate git repo with its own `origin = Mueve-TEC/odoo-argentina`):
   ```bash
   cd submodules/odoo-argentina
   ./scripts/pull-upstream.sh <name>   # one of the five keys above
   ```
   Produces a `Squashed …` + `Merge commit …` pair; resolve conflicts
   normally (`git add`, `git commit`), then commit the bumped submodule
   pointer in the supermodule.
5. `mueve-modules/` is the **only home for Mueve's own modules**
   (`l10n_ar_inflation_adjustment`, `eh_account_base`,
   `eh_account_reconcile_pro`). New Mueve modules go here; overrides for
   upstream modules also belong here rather than editing `adhoc-modules/`
   in place (though in-place edits under `[FIX-adhoc]` are allowed when an
   override module is impractical).
6. **`soltec-localdev-odoo19` itself is explicitly out of scope of the
   localization migration** (PLAN.md, "what we deliberately did NOT do"):
   bumping the supermodule's `submodules/odoo-argentina` pointer and
   re-running `copy_addons.sh` is a separate step the agent will often need
   to perform.

OCA pristine repos declared but **not** vendored (for whoever wants to
materialize them with gitaggregate): `partner-contact`, `reporting-engine`
(seen in `submodules/odoo-argentina/oca_dependencies.txt`).

### Synchronizing modules into the addons path

In the supermodule, after pulling submodule updates:

```bash
bash copy_addons.sh        # o:  make sync
```

`copy_addons.sh` recursively finds every `__manifest__.py` under
`./submodules/` (excluding `.git/`), rsyncs each module dir to
`custom-addons/<basename>` with `--delete`, and then removes orphan dirs in
`custom-addons/` that lack an `__manifest__.py` (handles upstream renames
like `l10n_ar_afipws` → `l10n_ar_fiscal_ws`). `exclude.txt` strips `*.txt`,
`*.md`, `setup/`, dotfiles, `LICENSE`, `README.rst`, and all lint config
(`.flake8`, `.pylintrc`, `.pre-commit-config.yml`, `.eslintrc.yml`,
`.prettierrc.yml`, `.isort.cfg`, `.copier-answers.yml`, `.editorconfig`)
from the copy — so **lint config does not reach `custom-addons/`** and is
not what Odoo loads.

Dependencies for the AR web-service modules are **NOT baked into the image** —
the `Dockerfile` is bare (`FROM odoo:19.0`). The migrated modules
(`l10n_ar_fiscal_ws*`) run on `zeep` + `pyOpenSSL`, both already present in
the base `odoo:19.0` image, so they need nothing extra. The **legacy
pre-rename modules** (`l10n_ar_afipws*`) still `import pyafipws` /
`pysimplesoap`; if those load, install
`submodules/odoo-argentina/requirements.txt` into the running container
(see "Python / Dependency Management" and Gotcha #9). There is **no** host
`pip` workflow; the only `requirements.txt` is meant to be `pip install -r`'d
into the Odoo container.

## Testing

**There is no project-level test runner, no `pytest.ini`, no project-level
test config, and no CI in `soltec-localdev-odoo19`.** The docker compose
`command` does not include `--test-enable`.

How tests are actually run here:

1. **Drop into the running Odoo container** and invoke Odoo's built-in test
   runner with `--test-enable` and `--test-tags`. From the repo root:
   ```bash
   docker compose exec web odoo \
     --addons-path=/mnt/custom-addons,/usr/lib/python3/dist-packages/odoo/addons \
     -d <odoo_db> \
     --test-enable \
     --test-tags=/odoo-unc.migracion.soltec-localdev-odoo19:migra:module-name \
     --stop-after-init \
     -u <module_name>
   ```
   (concrete syntax below in Useful Commands).
2. **Per-module data migrations** (the `migrations/<version>/` dirs) run
   automatically on `-u <module>`.

Existing test coverage in the tree is sparse and lives **inside the OCA /
ADHOC submodules**, in `eh_account_base`, and (since 2026-08-06) in the ARCA
web-service modules:

- `custom-addons/*/tests/` present for ~35 modules: OCA
  `bank-statement-import` / `account-reconcile`, ADHOC `account-payment` /
  `account-financial-tools`, plus new suites in `l10n_ar_fiscal_ws` /
  `l10n_ar_fiscal_ws_fe` (`test_data_urls`, `test_padron_errors`,

### Lint scoping — important

`pre-commit` uses the `.pre-commit-config.yaml` at the **git top-level** of
the current repo, and `pre-commit run --all-files` only scans files tracked
by *that* repo. Consequences in this project:

- **Supermodule**: `git ls-files` tracks each submodule as a single **gitlink**
  (a commit pointer), not the files inside it. So `make lint` at the
  supermodule root only scans supermodule infra files (`Dockerfile`,
  `docker-compose.yml`, `Makefile`, `copy_addons.sh`, `README.md`, `AGENTS.md`,
  `pyproject.toml`, `.pre-commit-config.yaml`, `docker/*.sh`, `exclude.txt`).
  It **does not** see anything under `submodules/<repo>/...` — that code lives
  in separate git repos.
- **`submodules/odoo-argentina`**: has its own root `.pre-commit-config.yaml`
  that recreates the **adhoc stack** (pre-commit-hooks, OCA odoo-pre-commit-hooks,
  ruff, pylint-odoo, rstcheck — see below). Run `make lint-odoo-ar` (or
  `cd submodules/odoo-argentina && pre-commit run --all-files`) to apply it.
  This covers `mueve-modules/` **and** the `adhoc-modules/*` subtrees.
- **`submodules/bank-statement-import/` and `submodules/account-reconcile/`**:
  OCA repos with their own root `.pre-commit-config.yaml` (the heavier OCA
  template: ruff + pylint-odoo + oca-checks + whool + maintainer-tools +
  prettier + eslint). Run `cd <repo> && pre-commit run --all-files`.
- **`submodules/odoo-union/` and `submodules/odooapps/`**: **no pre-commit
  config** of their own, and invisible to the supermodule's. They have no
  automated lint. If needed, run ruff manually: `ruff check submodules/odoo-union`
  (and `--fix`). `odooapps` is third-party (odoomates) — treat as read-only.
- **Dormant subtree configs**: `submodules/odoo-argentina/adhoc-modules/*/.pre-commit-config.yaml`
  each carry the ingadhoc copier template, but because pre-commit reads the
  repo top-level config, these are **not used** when running from the
  `odoo-argentina` root (the new root config supersedes them). They remain as
  upstream-origin documentation; to apply one explicitly use
  `pre-commit run --all-files --config adhoc-modules/<sub>/.pre-commit-config.yaml`.

The OCA / ingadhoc stack used inside the submodules is, e.g. for
`submodules/bank-statement-import/.pre-commit-config.yaml`:

- **ruff** (`ruff --fix` + `ruff-format`, astral-sh/ruff-pre-commit `v0.13.0`)
- **pylint-odoo** (`OCA/pylint-odoo` `v9.3.15` — `pylint_odoo` with

### Run tests for a module

The `Makefile` wraps the most common case. Use Odoo's `--test-enable` plus
`--test-tags` to narrow scope. Convention: add `--log-level=info` and tail
for `PASS`/`FAIL`/`ERROR`.

```bash
# Todos los tests de un módulo (vía Makefile — upgrades + --test-enable):
make test MODULE=<module_name>

# Con un filtro --test-tags:
make test MODULE=<module_name> TEST_TAGS=/soltec:<module>

# Instalación fresca del módulo + tests:
make test-install MODULE=<module_name>
```

Equivalentes raw (dentro del container):

```bash
# All tests for one module (must upgrade it so the test package loads):
docker compose exec web odoo \
  -d <db> \
  --test-enable \
  --test-tags=/odoo-unc.migracion.soltec-localdev-odoo19:migra:module-name \
  -u <module_name> \
  --stop-after-init \
  --log-level=info

# Just the standard "at_install" + "post_install" tagged tests for a module:
docker compose exec web odoo \
  -d <db> \
  --test-enable \
  --test-tags=/odoo-unc.migracion.soltec-localdev-odoo19:migra:module-name:at_install,/odoo-unc.migracion.soltec-localdev-odoo19:migra:module-name:post_install \
  -u <module_name> --stop-after-init

# Run a single test class/method by test-tags (use a custom @tagged('soltec','<module>')):
docker compose exec web odoo -d <db> --test-enable --test-tags=soltec.<module> -u <module> --stop-after-init
```

> Note: Odoo's `--test-tags` filters by _module path_ (`module.Class.method`
> syntax) and/or custom tags. The leading `/` form matches tags, not paths,
> so a typical "run everything in module X" is just `--test-tags=<module_name>`
> when tests are tagged with the module name (common OCA pattern).

## Conventions & Gotchas

1. **Never edit `custom-addons/` in place.** It is gitignored and regenerated
   by `copy_addons.sh`. Make edits in the proper `submodules/<repo>/...` module
   dir, then `bash copy_addons.sh`, then `docker compose up -d` (or restart Odoo).
2. **Two repos have an `origin` you can push to**:
   - `soltec-localdev-odoo19` → `Mueve-TEC/soltec-localdev`.
   - `submodules/odoo-argentina` → `Mueve-TEC/odoo-argentina` (this is where AR
     localization fixes and `mueve-modules/` commits go).
     Other submodules (`odoo-union`, `odooapps`, `bank-statement-import`,
     `account-reconcile`) are third-party (Mueve-TEC / odoomates / OCA); treat
     them as read-only unless you have push rights there.
     `odoo-union` is currently checked out in a **detached HEAD** state at
     commit `93d26f6` — check out its `19.0` branch before committing to it.
3. **`[FIX-adhoc] <module>: <description>`** is the required commit-message
   prefix for in-place fixes to `adhoc-modules/` inside `odoo-argentina`
   (rhymes with OCA's `[FIX]` convention but signals "local patch on vendored
   upstream, not sent upstream"). Audit them with:
   `git -C submodules/odoo-argentina log --grep='^\[FIX-adhoc\]' --name-only -- adhoc-modules/`.
4. **Migration-incomplete modules** that will not work cleanly on Odoo 19 yet
   (because their code is still Odoo 18/16):
   `l10n_ar_inflation_adjustment` (18.0.1.0.0), `l10n_ar_reports` (16.0.1.0.0),
   `l10n_ar_tax_ratio` (18.0.1.0.0), `account_payment_multi` (18.0.1.1.0),
   `account_financial_amount` (13.0.1.0.0). They are present in `custom-addons/`
   but may fail to install / upgrade. (`l10n_ar_pos_afipws_fe` was migrated to
   19.0 in PR #2 and is now installable.) When asked to migrate one, the
   typical Odoo-19 changes are:
   view `tree`→`list`, `attrs`→inline `invisible`/`readonly`/`required`,
   `states=` dropdown-removal, `name_*` → `<field name="..."/>` in views,
   `_post_init_hook(env)` / `post_init_hook(cr, e)` signature alignment, and
   recomputing/storing any field whose compute depends on changed APIs.
5. **Renamed modules**: `l10n_ar_afipws` → `l10n_ar_fiscal_ws` and
   `l10n_ar_afipws_fe` → `l10n_ar_fiscal_ws_fe` (done upstream by adhoc-dev's
   migration branch `19.0-mig-MAQ`, PR #92 to ingadhoc). Both old and new
   names coexist temporarily in `custom-addons/` — `copy_addons.sh`'s
   "orphan cleanup" only removes dirs without `__manifest__.py`; renames where
   the old module still has a manifest will NOT be auto-pruned. The
   `l10n_ar_tax_backward_compatibility` shim bridges old→new behaviour.
6. **Odoo 19 image quirk**: `docker-compose.yml` passes only `--addons-path`
   to the web service, not a DB filter. If you create multiple databases,
   Odoo will prompt for the master DB password and list all DBs on the
   manager page. Use `-d <db>` explicitly on every CLI invocation above.
7. **Per-module data migrations** (the standard Odoo
   `<module>/migrations/<version>/pre-migrate.py` & `post-migrate.py`) exist
   only for `account_payment_pro` (`19.0.2.0.0` and `19.0.2.11.0`). These run
   on `-u account_payment_pro` automatically. If you bump a module version,
   you may need to create a `migrations/<new_version>/` dir with
   `pre-migrate.py` / `post-migrate.py` for data backfills.
8. **No CI runs from this repo.** Tests / pre-commit only run upstream in the
   submodule repos (OCA / ingadhoc have the GitHub workflows). When you push
   to `Mueve-TEC/odoo-argentina` remember its PRs/branches are what's CI'd —
   keep commits there self-contained.
9. **`requirements.txt` is for the container, not the host.** The AR
   web-service modules need `pyafipws` (Mueve fork, `py3k` branch) — but only
   the **legacy pre-rename modules** (`l10n_ar_afipws*`) actually `import` it;
   the migrated `l10n_ar_fiscal_ws*` modules use `zeep` (already in the image)
   instead, so they work with no extra install. Since the `Dockerfile` is bare
   (`FROM odoo:19.0`), if you load a legacy module, install the deps into the
   running container with `docker compose exec web pip install -r ...`
   (or add a `RUN pip install` to the `Dockerfile` and `make build`).
10. **Branch model**: develop on `19.0` (current). The `18.0` branch is the
    older generation; `main` is the README/infra-only branch
    (`origin/HEAD -> origin/main`). Don't mix module commits between versions.
11. **Stray artifacts**: the empty `.qodo/agents/` & `.qodo/workflows/` dirs
    are not used by the runtime — safe to delete if cleaning up. (The empty
    `git@github.com:Mueve-TEC/` directory that used to sit at the repo root
    was an accidental `git clone` artifact and has been removed.)
12. **Makefile `install`/`upgrade`/`test` targets don't work as-is in this
    setup.** They don't pass `--addons-path` (and the image's `/etc/odoo/odoo.conf`
    points at a non-existent `/mnt/extra-addons`), and `docker compose exec web
    odoo` bypasses the entrypoint env vars, so DB host/user/password are unset.
    For any CLI run use the raw form:
    ```bash
    docker compose exec web odoo \
      --addons-path=/mnt/custom-addons,/usr/lib/python3/dist-packages/odoo/addons \
      --db_host=db --db_user=odoo --db_password=odoo \
      -d <db> -u <module> --stop-after-init --http-port 8099
    ```
    Use `--http-port 8099` (a free port): `--no-http` does **not** prevent the
    "Address already in use" bind error when the web container is running. This
    is the tested pattern for upgrades and `--test-enable` runs.
13. **`arcaws.env.type` changes take effect without a server restart.** The
    environment is read live (via `search()` on the config parameter) and the
    web-service URLs are not ormcached, so switching homologation↔production
    applies immediately. An explicitly-set **invalid** value raises a
    `UserError` (no silent fallback to production). The warning surfaces as a
    blocking popup on the padrón direct/mass actions and as a persistent banner
    in the "Update Partners From Padron ARCA" wizard.
